# Important Instructions

The report should be written as a professional document intended for the client of the proposed system.

The report should not be written as a personal assignment submission. It must be written in the third person and should avoid personal pronouns such as:

* “I”
* “We”
* “You”

The content under each subsection should be explained in sufficient detail.

## 2.4 Risk Feasibility

This section should identify possible risks that could affect the project and describe suitable mitigation strategies.

Possible risks include the following.

### Requirements Risk

**Risk:** Requirements may be incomplete, unclear, or changed during development.

**Mitigation:** Conduct regular discussions with the client, document requirements clearly, validate prototypes, and maintain a controlled process for requirement changes.

### Schedule Risk

**Risk:** Development tasks may require more time than initially expected.

**Mitigation:** Divide the project into manageable stages, prioritise essential features, monitor progress regularly, and maintain time buffers for high-risk tasks.

### Technical Integration Risk

**Risk:** Selected technologies or external services may not integrate correctly.

**Mitigation:** Develop early prototypes, test major integrations in advance, and identify alternative technologies.

### Data-Quality Risk

**Risk:** Input data may be incomplete, inconsistent, inaccurate, or poorly formatted.

**Mitigation:** Implement data-validation mechanisms, allow manual correction, maintain data-quality checks, and clearly communicate input requirements.

### Security Risk

**Risk:** Unauthorised users may gain access to sensitive data or system functions.

**Mitigation:** Use secure authentication, role-based access control, encryption, audit logging, secure coding practices, and regular security testing.

### Privacy Risk

**Risk:** Personal or confidential information may be exposed or used improperly.

**Mitigation:** Collect only necessary data, obtain appropriate consent, restrict access, encrypt sensitive data, and establish data-retention policies.

### External-Service Risk

**Risk:** Third-party services, APIs, or cloud platforms may become unavailable or change their pricing or functionality.

**Mitigation:** Minimise unnecessary dependencies, implement error-handling mechanisms, monitor service usage, and identify alternative providers.

### Performance Risk

**Risk:** The system may become slow when processing large amounts of data or serving many users.

**Mitigation:** Conduct performance testing, optimise database queries, use caching where appropriate, and design the architecture to support scaling.

### User-Adoption Risk

**Risk:** Intended users may find the system difficult to use or may resist replacing existing processes.

**Mitigation:** Involve users during design, conduct usability testing, provide training materials, and introduce the system gradually.

> **Important:** Do not state that unfamiliarity with a technology is itself a project risk.

The report should focus on risks associated with the system, development process, operating environment, and client requirements.

# 3. Considerations

This section should discuss the primary quality concerns and important system characteristics.

## 3.1 Performance

The system should provide acceptable response times and should be capable of processing the expected number of users, requests, and records.

Performance considerations may include:

* Response time
* Processing speed
* Database-query efficiency
* Network usage
* Concurrent users
* File-processing time
* Scalability

## 3.2 Security

The system should protect its data, users, and functions against unauthorised access and misuse.

Security considerations may include:

* Secure authentication
* Password protection
* Role-based access control
* Data encryption
* Session management
* Input validation
* Audit logs
* Secure backups
* Protection against common web vulnerabilities

## 3.3 Privacy

The system should collect and process only the information required for its intended functions.

Privacy considerations may include:

* User consent
* Data minimisation
* Access restrictions
* Data-retention periods
* Secure deletion
* Confidentiality
* Transparency regarding data usage

## 3.4 Usability

The user interface should be simple, consistent, and understandable for its intended users.

Usability considerations may include:

* Clear navigation
* Readable content
* Meaningful error messages
* Consistent interface elements
* Reduced number of unnecessary steps
* User guidance
* Responsive design

## 3.5 Accessibility

The system should be usable by individuals with different abilities and technical backgrounds.

Accessibility considerations may include:

* Keyboard navigation
* Screen-reader compatibility
* Text alternatives for images
* Sufficient colour contrast
* Adjustable text sizes
* Clear language
* Accessible form labels

## 3.6 Reliability

The system should operate consistently and recover appropriately from failures.

Reliability considerations may include:

* Error handling
* Backup and recovery
* Data consistency
* System monitoring
* Service availability
* Recovery from interrupted operations

## 3.7 Maintainability

The system should be designed so that faults can be corrected and future improvements can be introduced efficiently.

Maintainability considerations may include:

* Modular architecture
* Clear documentation
* Coding standards
* Automated testing
* Version control
* Configuration management
* Separation of system components

## 3.8 Scalability

The system should support reasonable increases in users, stored data, and processing demand.

Scalability may be achieved through:

* Efficient database design
* Cloud infrastructure
* Load distribution
* Caching
* Modular services
* Horizontal or vertical scaling

## 3.9 Accuracy

Where the system performs calculations, predictions, classifications, information extraction, or automated decision support, the accuracy of the results should be evaluated.

The system should provide mechanisms for:

* Input validation
* Result verification
* Error correction
* Confidence reporting
* Manual review
* Performance evaluation

## 3.10 Ease of Use

The system should minimise the effort required to complete common tasks.

Important features may include:

* Simple forms
* Search and filtering
* Clear instructions
* Helpful notifications
* Automated data entry
* Progress indicators
* Confirmation messages
* Appropriate default values
